# Переиспользуемый identity-lock и negative-профили для подготовки ракурсов

Дата: 2026-11-04
Статус: реализовано; `attempt-002` принят пользователем как рабочий вариант несмотря на упрощение снаряжения. Следующий обязательный этап: маска неизменяемых элементов (наплечник, разные наручи, ботинки, характерные черты), чтобы генерация меняла только позу и не перерисовывала защищённые области.

## Цель

Переделать подготовку A-pose и ракурсов MV-Adapter в чистый переиспользуемый этап, который:

- не подменяет характерные черты исходного изображения;
- не дублирует и не симметризует снаряжение без основания;
- отделяет общие правила сохранения идентичности от описания конкретного объекта;
- позволяет независимо выбирать negative-профиль для персонажа, здания или другого типа источника;
- не пропускает визуально бракованные изображения в shape и texture;
- сохраняет попытки, параметры и результаты проверки для воспроизводимости.

## Подтверждённая проблема

Сравнение `data/runtime/orc/views/raw/front.png`, `data/runtime/orc-apose/apose-front.png` и текущих четырёх ракурсов показало:

- A-pose изменил нос, челюсть, бороду, клыки и детали лица;
- разные наручи и сапоги исходника стали симметричными;
- наплечник был перепроектирован;
- боковые ракурсы содержат длинный клинообразный выступ вместо правдоподобного профиля.

Текущие A-pose и ракурсы орка отклонены и не должны использоваться для shape. Добавление запретов только в negative prompt не устраняет причину: генеративная модель всё равно домысливает невидимые части исходника.

## Термины и границы ответственности

### Identity-lock

Общие положительные инварианты редактирования исходника. Не содержит орк-специфичных цветов, одежды или анатомии.

Разрешает менять только позу, положение конечностей, ракурс и компоновку кадра. Требует сохранять:

- геометрию носа, подбородка, челюсти, глаз, ушей и других характерных черт;
- клыки, шрамы, причёску и пропорции, если они есть у источника;
- количество, расположение и асимметрию снаряжения;
- стиль, материалы и цвета;
- отсутствие новых предметов и повторов существующих.

Identity-lock не обещает невозможного: по одному изображению нельзя достоверно восстановить невидимую геометрию. Его результат обязательно проходит визуальную проверку.

### Preset объекта

Отдельная версионируемая JSON-структура с описанием конкретного источника. Для персонажа может содержать:

- `kind`: тип объекта, например `character` или `building`;
- `identityFeatures`: характерные черты, которые нельзя перепроектировать;
- `inventory`: предметы, их количество и сторону размещения;
- `asymmetry`: различия левой и правой стороны;
- `viewNotes`: особые требования к профилю и заднему виду;
- `positive`: короткое описание объекта для сборки промта;
- `version`: версию пресета.

Пресет орка должен явно описать один наплечник на конкретном плече, разные наручи и разные сапоги. Для нового персонажа создаётся новый JSON без изменения программного кода.

### Negative-профиль

Отдельная именованная JSON-структура, не встроенная в identity-lock или preset объекта.

Начальный набор:

- `character`: анатомические дубли, лишние конечности, повторы снаряжения, нежелательная симметризация, обрезка;
- `building`: лишние этажи, окна, двери, башни, дублированные крылья, изменение конструкции, обрезка;
- `generic`: только общие дефекты изображения без правил конкретного типа объекта;
- `none`: пустой negative prompt для контролируемых экспериментов.

Пользовательский JSON может заменить именованный профиль. Negative-профиль выбирается отдельной опцией и одинаково доступен этапам A-pose и views. Орк-специфичные запреты не должны попадать в профиль здания.

Negative prompt является вспомогательным фильтром. Длинный список запретов не считается доказательством сохранения идентичности.

## Архитектура

### 1. Разрешение конфигурации

Единый resolver получает:

- путь к preset объекта;
- имя negative-профиля или путь к пользовательскому JSON;
- назначение промта: `apose` или `views`;
- необязательные дополнительные инструкции пользователя.

Он возвращает immutable-результат:

- resolved positive prompt;
- resolved negative prompt;
- версии identity-lock, preset и negative-профиля;
- канонические исходные данные для manifest и хеширования.

A-pose и MV-Adapter используют один resolver. В workflow-файлах не остаётся отдельных глобальных `APOSE_PROMPT`, `APOSE_NEGATIVE`, `ORC_VIEW_PROMPT` и `ORC_VIEW_NEGATIVE`, которые можно случайно рассинхронизировать.

### 2. CLI

Обе команды получают явные параметры:

- `--preset <path>` — обязательный preset объекта;
- `--negative-profile <character|building|generic|none>` — именованный профиль;
- `--negative-file <path>` — пользовательский профиль, взаимоисключающий с `--negative-profile`;
- `--output <path>` — корень новой серии попыток.

Понятные значения по умолчанию допустимы только для negative-профиля: `character` для preset с `kind: character`, `building` для `kind: building`, иначе `generic`. Тип объекта и его описание не угадываются по имени файла.

Некорректный JSON, неизвестный профиль, конфликт опций или отсутствующие обязательные поля останавливают запуск до старта ComfyUI и до расходования GPU-времени.

### 3. Попытки и неизменяемость результатов

Каждый запуск создаёт отдельный каталог:

```text
<output>/
  attempts/
    attempt-001/
      apose-front.png
      manifest.json
      review.json
    attempt-002/
      ...
```

Существующие попытки не перезаписываются. В manifest сохраняются:

- абсолютные или воспроизводимо разрешимые пути;
- SHA-256 исходника и созданных изображений;
- seed, steps, размер и backend;
- resolved prompt/negative;
- preset, negative-профиль и их версии/хеши;
- workflow или его воспроизводимое описание;
- статус выполнения и ошибка;
- время этапов.

Имя ComfyUI-файла не является идентификатором попытки и не используется для перезаписи предыдущих результатов.

### 4. Визуальные барьеры

#### Барьер A-pose

До запуска views создаётся лист сравнения исходника и A-pose. Проверяются:

- нос, подбородок, челюсть, глаза, уши, клыки, шрамы и причёска;
- пропорции тела или конструкции;
- инвентарь и стороны размещения;
- дубли и самопроизвольная симметризация;
- полнота кадра и конечности/части объекта.

Результат: `pending`, `approved` или `rejected` с комментарием. По умолчанию — `pending`.

#### Барьер четырёх ракурсов

До shape создаётся contact sheet. Каждый ракурс проверяется отдельно, а вся партия — на взаимную согласованность:

- профиль не содержит выдуманного носа, челюсти или клина лица;
- черты и снаряжение совпадают между ракурсами;
- стороны асимметричных предметов не перепутаны;
- нет дополнительных предметов, конечностей или повторов;
- front из той же партии MV-Adapter не заменяется другим front без явной записи в manifest.

Партия получает `approved` только после явной визуальной приёмки. Shape требует approved manifest; `pending`, `rejected`, отсутствующий или несовпадающий по хешам manifest блокирует запуск.

Автоматические проверки могут подтвердить файлы, размеры, alpha, обрезку и хеши, но не объявляются доказательством идентичности. Окончательную визуальную приёмку выполняет человек.

### 5. Повторные попытки

Отклонённый результат сохраняется с причиной отклонения и не затирается.

Для A-pose повтор создаёт новую попытку с новым seed или изменённым preset. Для MV-Adapter по умолчанию повторяется вся согласованная партия. Ракурсы из разных партий нельзя незаметно смешивать: это нарушает взаимную согласованность. Выборочная перегенерация одного ракурса допускается только как отдельный явно помеченный эксперимент после проверки возможностей backend.

Shape и texture не запускаются автоматически после генерации ракурсов.

## Ограничения реализации

- Без новых моделей, скачиваний и смены backend в первой реализации.
- Сохраняются Qwen-Image-Edit-2509 Q4_K_M и существующий MV-Adapter.
- Без установки или замены драйверов, изменения сети, VPN, WSL и системного Python.
- Без production-ready флагов и обновления `native-ready.json`.
- Без запуска Standard 1024 и UV 2048/4096 для этой задачи.
- Длительные GPU-запуски выполняются последовательно и только после отдельного согласования команды запуска.
- При OOM выполнение останавливается; веса и backend не подменяются.

## Тестирование

### Модульные тесты

- resolver собирает одинаковые инварианты для A-pose и views;
- preset орка не попадает в preset или negative-профиль здания;
- `character`, `building`, `generic`, `none` и пользовательский JSON разрешаются независимо;
- конфликтующие CLI-опции и невалидные JSON отклоняются до запуска;
- resolved manifest содержит промты, версии, seed и хеши;
- повторный запуск выбирает новый attempt и не перезаписывает прежний;
- shape отклоняет `pending`, `rejected`, отсутствующий manifest и изменённые после приёмки файлы;
- старые RGBA `norm/cut_*.png` остаются входом shape после approved views.

### Интеграционная проверка без GPU

На сохранённых изображениях орка проверяется полный переход:

`preset + negative profile -> resolved prompts -> attempt manifest -> rejected review -> shape blocked`.

Затем тестовая копия manifest с явным approved статусом пропускает только синтетический dry-run, не реальный shape.

### Визуальная проверка с GPU

Только после прохождения тестов и отдельной команды пользователя:

1. Новая A-pose попытка орка.
2. Визуальная приёмка лица и снаряжения.
3. Только после approved A-pose — новая партия ракурсов.
4. Визуальная приёмка каждого ракурса.
5. Только после approved views — отдельное решение о light shape.

Текущие изображения орка остаются отклонёнными regression-образцами и не становятся approved для удобства прохождения конвейера.

## Критерий готовности

Задача считается выполненной, когда:

- общий identity-lock, preset объекта и negative-профиль независимы;
- один и тот же механизм работает минимум для тестовых preset персонажа и здания без изменения кода;
- все параметры попадут в воспроизводимый manifest;
- повторные запуски не затирают результаты;
- визуально отклонённые A-pose/views технически не проходят в shape;
- тесты и документация отражают фактическое поведение;
- никакой реальный результат не объявлен визуально принятым без просмотра.
